# AdaptiveRoute Architecture

AdaptiveRoute is a proof of concept for last-mile route planning and route replanning under operational disruptions. The system combines an exact prescriptive optimizer, a fine-tuned route-policy model, a general-purpose local LLM for interaction, persistent memory, RAG, and a React operational console.

The central architectural decision is that the LLM is not the source of truth for feasibility. Route candidates generated by the trained model are always parsed, validated, optionally repaired, and backed by Pyomo + HiGHS fallback.

|---|---|---|
| React frontend | `frontend/` | Admin and driver workspaces, maps, route selection, chat, CRUD flows. |

| Training | `src/adaptiveroute/training/` | Dataset construction, prompt formatting, auditing and prediction evaluation. |

## Runtime Roles

### Admin

The admin workspace is used to create scenarios, ingest orders, run the solver, monitor routes, manage drivers and inspect agentic behavior. The admin dashboard can select one or more driver routes and visualize only those routes on the map. If no route is selected, the map remains visible with scenario points but without route polylines.

### Driver

The driver workspace is scoped to the logged-in driver. It shows only assigned routes, route metrics, route map, and a chat interface to report disruptions or ask route-specific questions. The driver can update route status and manage profile settings such as password and vehicle capacity.

## Model Responsibilities

| Capability | Model / Engine | Role |
|---|---|---|
| Exact planning | Pyomo + HiGHS | Prescriptive source of truth. |
| Fast route candidate | Fine-tuned LoRA, `adaptiveroute-routing-policy` | Approximate route proposal under disruptions. |
| Natural-language interaction | Local general LLM, `chat-local` | Explanations, route Q&A, operational reasoning and follow-ups. |
| Guardrails | Deterministic validator | Feasibility authority. |

## Storage Design

MongoDB stores operational application state where document-shaped records are natural:

- conversations;
- messages;
- rolling context windows;
- agent runs/traces;
- scenarios;
- drivers;
- operational routes;
- planning jobs.

PostgreSQL + pgvector stores retrieval chunks and embeddings for documentation-based RAG.

The repository layer provides in-memory alternatives for tests and local smoke runs.

## Deployment Shape

The default Docker stack contains:

- `api`: FastAPI backend;
- `frontend`: React/Vite development server;
- `mongo`: operational and memory persistence;
- `postgres`: pgvector RAG persistence;
- optional `osrm`: road-distance and road-geometry backend;
- optional `api-gpu`: backend profile for direct local LoRA loading.

The local OpenAI-compatible LLM API can run outside the Docker Compose stack and be accessed by the API container through `host.docker.internal`.
